# 放号前登录更新

启用设置中的“放号前刷新登录，失效时自动恢复”后，定时抢场会在放号前主动刷新官方窗口，等待新 Token 并验证。默认提前 120 秒：20:00 放号对应 19:58。自定义放号时间或提前量仍按任务设置执行。

## 使用条件

- 企业微信保持登录，官方预约窗口保持打开，现有刷新器能够识别窗口。
- 本地捕获链路已接入并成功捕获过登录信息。仅粘贴页面脚本、未接入代理捕获时，不会强行整页刷新。
- 自动恢复开关须已启用；升级不会擅自修改开关、测试模式或预约目标。
- 任务应提前设置。临近放号才启动会压缩刷新时间，不能保证赶上。

验证旧 Token 成功不等于续期。准备时优先等待新值、认证版本更新并验证成功。如果刷新保留了原 Token，会额外执行一次只读验证；只有验证成功且登录状态允许下单，才继续等待，并明确显示“不代表续期”。鉴权失败、网络异常或降级状态不会通过这条回退路径。登录过期需要重新登录时，仍需本人操作。

登录刷新没有时间冷却，`retry_in_sec` 固定为 0。并发到达的恢复请求共用一次尝试，后续明确的新请求可以立即重试；每次尝试仍有次数及超时边界，不会无限刷新。准备失败后，近期重新同步、认证版本更新且验证通过的登录可直接采用，不必再刷新一次。

同一放号时间的两个运动共用准备结果。鉴权失败后复用已完成的恢复验证，避免重复查询。长轮扫描不再额外等待完整轮间间隔，但每秒一次的共享请求预算和服务端退避仍保留。

## 离线验收

在隔离的 `SUSTECH_DATA_DIR` 下运行：

```powershell
python -m unittest discover -s tests -p test_auth_keeper.py
python -m unittest discover -s tests -p test_rush_engine.py
node tests/check_inline_scripts.cjs
```

这两组测试共 54 项，使用模拟响应，不发送官方查询、验证码或订单。覆盖刷新未换 Token 后的成功/失败复验、无冷却重试、人工重新同步、双运动共享准备、订单在途不刷新，以及原有 Rush 扫描节奏。实际运行新代码前，需要在没有抢场或监控任务时重启后台服务。

## 边界与人工验收

- 当前 Token 验证通过只证明验证时可用，不能保证放号时仍有效；放号查询的鉴权失败继续走现有有界恢复。
- 捕获链路未接通或订单正在处理时，不执行上述刷新/回退验证。
- 两运动共用登录、HTTP 预算和订单保护，不代表两边一定预约成功。
- 升级后先确认服务正常、原有测试模式未变，再由本人配置任务；不要用真实订单作为安装验收。
- 采集重启测试使用明确前进的模拟时钟，避免 Windows 时钟刻度造成测试波动；未更改实际序号算法。系统时钟倒退导致采集序号被判陈旧仍是独立风险，不属于这次修复。
